## 追記：2026-09-06 保存保護の実装・検証

### 目的
「初回データ読込に失敗しても、保存済みデータを上書きしないこと」の実装・検証のみ。機能追加はしない。

### 対象・正本
Notion本体には本セッションから接続できなかったため、ユーザー依頼文（2026-09-06付）を実行用抜粋として使用した。Notionを読んだとは報告しない。

### 原因（現行コードで確認）
- [src/IListApp.jsx](../src/IListApp.jsx) の初回読込 `useEffect`（修正前）は `fetch("/api/data")` が失敗した `catch` 節でも `setLoaded(true)` を呼んでいた。
- 自動保存 `useEffect` は `loaded` のみを条件にPUTを行うため、読込失敗直後でも800ms後にその時点のstate（多くの場合SEED）をPUTしてしまう。
- 復旧タイミングによっては、保存待ち（800ms）の間にAPIが復旧し、保存済みサーバデータがSEED等で全置換されうる。

### 修正内容
- `loaded` を「初回読込が成功した場合のみtrue」にするフラグに変更。通信失敗・`!r.ok`・応答形式不正（`runs`/`regs`/`cert`の型不一致）はすべて失敗として扱い、`loaded`をtrueにしない。
- 失敗時は `save` を `"error"` にするのみで、`loaded`はfalseのまま維持。自動保存 `useEffect` は `loaded=false` の間は何もしない（既存のガード `if (!loaded) return;` がそのまま機能する）。
- 初回読込useEffectに `cancelled` フラグを追加し、アンマウント後の状態更新を防止。
- `SaveStatus` 表示を `loading`（読込中）/`saving`/`saved`/`error`（初回読込に失敗（保存は行われません））に整理し、失敗時に「保存済み」と誤表示しないようにした。
- 変更ファイル: [src/IListApp.jsx](../src/IListApp.jsx) のみ。

### 実行コマンドと結果
- `npm run build` … 成功（`vite build`、1500 modules transformed、`dist/`生成）。修正前・修正後の両方で実行し成功を確認。

### 指摘1：不正応答でも保存が許可される（修正済み）

- **現行コードで確認**：指摘のとおりであることを確認した。さらに、旧判定式に一時的に戻して検証ハーネスを実行したところ、シナリオAで **PUTが実際に1回発生**し、表示も誤って「サーバに保存済み」になることを実測で再現した（その後、修正版に戻して全件PASSを確認）。

### 指摘2：読込失敗と保存失敗の表示を分離（修正済み）

## 追記：2026-09-06 検証Mの観測方法の調査（本体変更が必要と判断し停止）

依頼により、検証Mの観測が本体の `setSave` に届いているかを調べた。**本体コードは変更していない。**

### 分かったこと（実測）

1. **従来のMの観測は機能していなかった。**
   `watchSaveSetter()` は `React.useState` を差し替えていたが、本体は名前付きimport
   `import React, { useState, ... } from "react"` の `useState` を使っている。

2. **原因**：Vite環境で `React`（default）と名前空間オブジェクトは**別物**である。
   - `React === NS.default` … true、`React === NS` … false
   - `React.useState` を差し替えても `NS.useState` は変わらない（実測で `.name` が別値になることを確認）
   - 本体の名前付きimportは `NS.useState` 側に束縛される

3. **名前空間側（`NS.useState`）の差し替えも届かなかった。**
   本体importより前に差し替え、差し替えが保持されていること（`NS.useState !== Real`）も確認したうえで、
   **ラッパは一度も呼ばれなかった**（呼出記録が空）。Viteの事前バンドルにより、
   本体の束縛がモジュール読込時点で確定しているためと考えられる。

4. **DOM観測では判定できない。** `SaveStatus` の表示変化を `MutationObserver` で観測する方法は、

### 変更案（採否はユーザー判断。未実施）

**案A：テスト用の観測フックを本体に1行だけ設ける（推奨）**
保存Effectの `applySave` 内で、`setSave` を呼ぶ直前に任意のフックを呼ぶ。

```js
const applySave = (next) => {
  if (!dropped && gen === saveGen.current) {
```

- **理由**：`setSave` に到達したかどうかを、アンマウント後でも確実に観測できる唯一の確実な手段。
  DOM描画に依存しないため、アンマウント後も「呼ばれた／呼ばれない」を区別できる。
- **保存ロジックへの影響**：分岐条件・送信内容・デバウンス・状態遷移は変更しない。観測点の追加のみ。
- **懸念**：本体にテスト専用のコードが入る。`?.` により本番では何も起きないが、
  「本番コードにテスト用フックを置かない」方針であれば採用できない。

**案B：`dropped` の効果を、アンマウントではなく別経路で確認する**
本体を変更せず、Mの対象を「アンマウント後」から
「同一Effectのcleanup後（次の変更で世代も進む経路）」に変える。
- **理由**：本体変更が不要。
- **限界**：その経路では世代判定でも弾けるため、**`dropped` 単独の効果は示せない**。
  依頼の「アンマウント後に状態更新の経路へ進まない」の確認にはならない。

**案C：現状維持（Mを削除または「観測不能」と明記して残す）**
- **理由**：誤ったPASSを出さないことを優先する。
- **限界**：アンマウント後の挙動は未検証のまま残る。

### 現時点の扱い
- 従来のMは**観測の有効性が未確認だった**ことを記録し、そのPASSを根拠として扱わない。
- `dropped` は、追加編集なしのアンマウント経路において**世代が一致したままであるため、唯一効いているガード**である
  （cleanupは世代を変更しないため）。前回の「防御的な二重化」という説明は誤りであり、上記のとおり訂正した。
