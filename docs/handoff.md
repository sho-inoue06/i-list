## 1. 原因

前回の実装は、保存`useEffect`の本体で世代を進めていた（`const gen = ++saveGen.current;`）。
世代が進むのがEffect実行時なので、**データ変更を受け付けてからEffectが走るまでの間**に到着した
旧PUT応答が `gen === saveGen.current` を満たし、`setSave` に進んでしまう。

この窓に入れるかどうかは、データ変更の経路によって異なることが実測で分かった。

| 経路 | 窓に入れるか | 理由 |
|---|---|---|
| 手入力（入力欄・セレクト） | **入れない** | React18はinput等のdiscreteイベントを同期的に流すため、`dispatchEvent`から戻った時点でEffectは実行済み |
| JSON読込（`importJSON`） | **入れる** | state更新が `FileReader.onload` の中＝discreteイベントの外で起きるため、受付とEffect実行の間に割り込める |

データ変更経路は `setRuns` / `setRegs` / `setCert` の3つに集約されており、
呼び出し元は「手入力（RunsEditor / RegsEditor / CertEditor）」「JSON読込（`importJSON`）」「初回読込の反映」である。

---

## 2. 再現できた条件

**JSON読込経路で再現した。** `FileReader.onload` をラップし、
`setRuns`/`setRegs`/`setCert` が呼ばれた直後・保存Effectの実行前に、保留していた旧PUTを解決させた。

観測した順序（修正前のコード）：

```
importAccepted                        ← setterが呼ばれた直後。表示は「保存中…」
staleReleased                         ← ここで旧PUTを解決
saveEffect(status=サーバに保存済み)      ← Effect実行時点で、旧応答により誤って「保存済み」になっている
```

**対照条件**（旧PUTを解決しない以外は同一）では、同じ位置が `saveEffect(status=保存中…)` になった。
表示が変わる原因が旧PUT応答であることを、この差分で切り分けた。

手入力経路については、狙った順序を作れなかった事実をそのまま記録する。
`dispatchEvent` から戻る前に保存Effectが実行されており、**この経路では再現していない**。
